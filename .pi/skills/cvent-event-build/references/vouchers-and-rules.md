# Event vouchers and advanced rules

Read [scope and intake](scope-and-intake.md), [registration and pricing](registration-and-pricing.md), and [verification](verification.md). These features are independently configurable per event. They are not discount codes, and a voucher is not an admission fee.

## Explicit toggles

First establish applicability using [scope and intake](scope-and-intake.md). If a voucher/rule is requested, necessary to a requested result or governed by an applicable approved baseline, establish its explicit enabled/disabled intent and required semantics; missing essential decisions remain unknown and block dependents. If optional and not requested, preserve the existing state and disclose it without completion credit; do not invent a toggle requirement solely because the category appears here. Blank is not off by itself; use documented field-specific semantics, never a universal blank convention. When enabled, require enough source detail to configure the exact semantics. When disabled, verify the saved disabled state; do not merely omit the section and claim compliance. Use a supported event-local toggle only. Do not delete rules/vouchers, change shared definitions or alter another event as a way to implement off. Report a removal/authority conflict instead.

## Event vouchers

Map exact name/code where applicable, value or entitlement, eligible type/admission/path, quantity/redemption limits, availability window/timezone, audience and requested active/display state. Inspect existing identities, reuse exact matches, edit authorized differences and create only confirmed missing event-only configuration. Record observed IDs so a partial save cannot lead to a duplicate.

Verify saved values AND redemption associations. Use a non-persisting preview only where supported; do not create attendee records, submit registrations, issue messages, make payments or redeem a live voucher to prove behavior. If required behavior cannot be tested safely, record it as untested.

## Advanced rules

For every rule record its exact trigger, conditions/operators/values, action, priority/precedence, affected fields/items/types/paths and enabled state. Preserve group/guest and required/show/hide semantics separately. Do not invent a condition from an informal rule name or copy a rule into an unrelated path.

Check dependencies before writing: referenced questions, choices, admissions, registration types and prices must exist with verified identity. Test both triggering and non-triggering cases, plus meaningful boundaries and conflicting-priority cases, in the non-persisting preview. Keep existing unrelated rules intact. External-system calculations or unavailable controls are blockers, not permission to approximate.

## Completion

A toggle being on or an object existing is insufficient. Record saved settings, scope/relationships, evidence and preview result. Pending or uncertain saves stop further mutations without replay. Include unsupported/missing input and untested behavior in the final INCOMPLETE report; DONE requires applicable rules and vouchers to meet the same verification standard as the rest of the event.
