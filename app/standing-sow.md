# Standing event-build scope

This is the current event-build scope distilled from `Finalized - EmeraldX_Timeline_Roadmap_v3.docx`, with the operator's later agreed changes. It is not the full historical delivery roadmap. The RR supplies this event's requirements and exact values; workbook template notes about what an agent can or cannot do do not override this scope or establish tool capability.

Implement applicable event details (dates/timezone/location/capacity), RR-supplied branding/assets, website/theme/header/footer/RR-required widget types, registration, admission items, pricing, paths, optional items, vouchers and advanced rules, including their dependencies. Do not build every available widget or option by default.

Reuse exact matches; create missing required objects and edit existing event-only differences, including admissions/prices/relationships—not duplicate workarounds or inspection-only reports. Preserve RR spelling, values and formatting; never invent defaults or suffixes. Resolve requirements across the workbook; missing inputs block dependent work, not unrelated executable requirements. Report blocked/untested work honestly, separately from genuine exclusions.

## Operator boundaries

Keep the upload-bound event identity/name fixed; never reset/clone it. Never delete/archive anything, including new objects/links. Never publish, send communications, access attendee/registrant records, configure sessions/speakers or affect other events. Leave the event unpublished as Draft.

Never modify existing shared/account-wide objects, definitions or defaults. Reuse exact shared matches; separate required shared creation needs demonstrated isolation from existing objects and other events. An event URL/new template alone does not prove isolation. No account administration, merchant/payment-account provisioning, banking/settlement changes, shared payment/tax/currency or credential/integration-identifier changes.

## Later delivery changes

Use RR workbook uploads and one native Pi, not a structured intake replacement or a closed/no-chat workflow. Operator template cloning, Azure/M365 deployment/review/approval/Outlook/triage, historical price estimates and automatic dollar ceilings, retry-from-failed-step, and separate guardrail/audit-trail/reference-event-acceptance deliverables are not this run's work. These exclusions do not remove operator boundaries or saved-result verification. No extra planner/reviewer, deterministic importer or prescribed execution sequence is required.
